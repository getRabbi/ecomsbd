# RedX — contract, as ecomsbd reads it

**Source:** RedX developer documentation, <https://redx.com.bd/developer-api/>
(RedX merchant site → Developer API). Read on 2026-09-23.

The page renders in the browser. Its content (endpoint table, status table,
delivery-type table, webhook text) is data in the page's own script,
`/_next/static/chunks/pages/developer-api-*.js`, served by redx.com.bd. It was
transcribed from there. Nothing here comes from a community package or blog.

The code transcription is `backend/app/couriers/redx/contract.py`. The
capability claims and their evidence are in
`backend/app/couriers/manifests/redx.yaml`.

## Connection

| | |
| --- | --- |
| Production | `https://openapi.redx.com.bd/v1.0.0-beta` |
| Sandbox | `https://sandbox.redx.com.bd/v1.0.0-beta` ("simulated, does not impact real data") |
| Auth header | `API-ACCESS-TOKEN: Bearer <token>` on every call |
| Credential | One token per environment, generated by the merchant ("Request token") |
| Token lifetime / refresh | Not documented |

Both hosts answer a missing or invalid token with `401`
`{"message": ..., "status_code": 401}` (observed without credentials).

## Endpoints

| Purpose | Method | Path | Used by ecomsbd |
| --- | --- | --- | --- |
| Track parcel | GET | `/parcel/track/{tracking_id}` → `{tracking: [{message_en, message_bn, time}]}` | client only |
| Parcel details | GET | `/parcel/info/{tracking_id}` → `{parcel: {..., status, delivery_type, charge, ...}}` | status polling |
| Create parcel | POST | `/parcel` → `{tracking_id}` | booking |
| Update parcel | PATCH | `/parcels` `{entity_type: "parcel-tracking-id", entity_id, update_details: {property_name, new_value, reason}}` → `{success, message}` | adapter `cancel` (status → `cancelled`) |
| Areas | GET | `/areas`, `?post_code=`, `?district_name=` → `{areas: [{id, name, post_code, division_name, zone_id}]}` | booking sheet area picker |
| Create pickup store | POST | `/pickup/store` | **never called** |
| Pickup stores | GET | `/pickup/stores` → `{pickup_stores: [...]}` | credential check, store choice |
| Pickup store details | GET | `/pickup/store/info/{id}` → `{pickup_store: {...}}` | quote (pickup area) |
| Charge calculator | GET | `/charge/charge_calculator?delivery_area_id&pickup_area_id&cash_collection_amount&weight` → `{deliveryCharge, codCharge}` | booking sheet quote |

### Create parcel fields

Required: `customer_name`, `customer_phone`, `delivery_area`,
`delivery_area_id` (integer), `customer_address`, `cash_collection_amount`
(string), `parcel_weight`, `value`.

Optional: `merchant_invoice_id`, `instruction`, `type` (reverse shipments),
`parcel_details_json`, `pickup_store_id`.

ecomsbd sends the required fields plus `merchant_invoice_id` (always),
`instruction` (when there is a note) and `pickup_store_id` (when the seller
chose a store). It never sends `type`, `parcel_details_json` or `is_closed_box`.
The last one appears only in the example request.

Where the field table and the example disagree on JSON type (`parcel_weight`,
`value` and `pickup_store_id` are strings in one and numbers in the other),
ecomsbd sends the example's numbers. `cash_collection_amount` is a string in
both and is sent as one, in whole taka.

Weight is sent in **grams**. Create says "appropriate units (e.g., kg, g)",
but Parcel Details and the charge calculator both state grams.

`delivery_area` and `delivery_area_id` are both required, and nothing
documents resolving a free-text address. So the seller picks the area from
`/areas` for every RedX booking, and ecomsbd never infers one.

## Statuses ("Status Updates and Meanings")

| Status | RedX's meaning | ecomsbd state |
| --- | --- | --- |
| `ready-for-delivery` | Parcel received from merchants | `PICKED_UP` |
| `delivery-in-progress` | Parcels have been dispatched to rider | `OUT_FOR_DELIVERY` |
| `delivered` | Parcels delivered by rider | `DELIVERED` (final) only when `delivery_type = regular`; `PARTIAL_DELIVERED` + quantities when `partial-delivery`; otherwise no change |
| `agent-hold` | Parcels are on hold to agent | `IN_TRANSIT` |
| `agent-returning` | Parcel return-in-progress | `RETURNING` |
| `returned` | Parcels returned | `RETURNED` (final) only when `delivery_type = regular`; otherwise no change |
| `agent-area-change` | Area change requested & in progress | no change |
| `paid` | Parcel amount is paid | no change (a settlement event) |
| `pickup-pending` | *(only in the Parcel Details sample; no meaning stated)* | no change |
| `cancelled` | *(the value Update Parcel writes to cancel)* | `CANCELLED` (final) only when `delivery_type = regular` |

Delivery types ("Delivery Type Reference Table"): `regular`, `reverse`,
`exchange-delivery`, `exchange-return`, `partial-delivery`, `partial-return`.

Any other status is stored exactly as sent. It changes nothing, and polling
continues.

## Webhook

- The merchant enters a callback URL on the developer page and enables it.
- RedX POSTs `application/json`:
  `{tracking_number, timestamp, status, message_en, message_bn, invoice_number, delivery_type}`.
- Authentication: "Any required credentials should be included in the query
  parameters of the URL", e.g. `https://example.com/callback?token=<token>`.
  There is no signature header.

ecomsbd issues each shop the URL
`/v1/webhooks/couriers/redx/<routing-token>?token=<secret>`. The routing token
selects the shop. The secret is generated, stored encrypted, and compared in
constant time. Bodies are stored and deduplicated by hash, since callbacks
carry no event id. `token=` values are scrubbed from log lines. As with Pathao,
a verified callback is recorded, and parcel state is kept current by polling.

## Not documented (so not relied on)

- What happens when a `merchant_invoice_id` is sent twice, or any way to find
  a parcel by it. An unconfirmed create stays `BOOKING_UNKNOWN`, is never
  re-sent, and is resolved by a person checking RedX's panel.
- Error body shape, rate limits, pagination, token lifetime.
- The reply RedX expects from a callback, and whether it retries.
- Bulk create, return requests, balance, payouts, customer history. None of
  these exist in the Open API.
