# ADR 0004 — Migrations are authored to run on PostgreSQL and SQLite

Status: Accepted · 2026-09-09 · Phase A

## Context

PostgreSQL is the production database (master spec section 29). The tests that
matter most — tenant isolation, migration sanity, the OTP and session rules —
need to run in CI and on a developer laptop. Requiring a PostgreSQL server for
`pytest` means those tests get skipped exactly when someone is in a hurry.

## Decision

Column types in `backend/app/db/types.py` are dialect-portable, with PostgreSQL
always getting the richer rendering:

- `GUID` -> native `uuid` on PostgreSQL, `CHAR(32)` elsewhere (`sa.Uuid`)
- `JSONColumn` -> `jsonb` on PostgreSQL, `JSON` elsewhere (`with_variant`)
- `TZDateTime` -> `timestamptz`, plus a decorator that normalises SQLite's naive
  return values back to aware UTC and refuses to store a naive datetime
- `Paisa` -> `BIGINT` everywhere

`migrations/env.py` renders these through a `render_item` hook so autogenerated
migrations import cleanly, and takes the database URL from application settings
rather than `alembic.ini` — a second copy of the connection string is how the
wrong environment gets migrated.

`TEST_DATABASE_URL` points the suite at a real PostgreSQL when one is available.

## Consequences

- `pytest` runs with no services on a clean checkout. This is why the isolation
  suite is not skippable.
- PostgreSQL-only behaviour is **not** exercised by default: `FOR UPDATE SKIP
  LOCKED` in the outbox falls back to a plain select on SQLite, and integrity
  error types differ. CI must also run the suite against PostgreSQL before a
  release; a SQLite-only green build is not sufficient evidence.
- Any future PostgreSQL-specific feature (partial indexes, RLS, generated
  columns) must be added in a guarded migration branch, or this ADR superseded.
